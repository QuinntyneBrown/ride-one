Pattern

Feedback and loading

Every action gets an answer: a busy button, a confirmed level, a toast, or a skeleton while the first status arrives.

Overview

Pick the lightest feedback that fits: the control itself (busy button, Setting 22…), then inline text, then a toast, then an alert. Skeletons for known layouts, the spinner only when the layout is unknown.

When to use

  • Busy buttons for actions the rider started (Start, End).
  • Pending target resistance under the level until the bike confirms.
  • Toasts for results that happen away from the control (slow to confirm, couldn't set).
  • Skeletons on first load of ride and setup.

States

  • Waiting under 1 s: nothing extra.
  • Waiting 1–5 s: busy state on the control.
  • Slow over 5 s: warning toast saying what Wattzup is doing (resending every 5 s).
  • Failed: danger toast or alert with Retry.

Responsive

  • Skeletons match the layout at each breakpoint so nothing shifts on load.
  • Toasts move to full width at the bottom below 640px.

Accessibility

  • Busy controls set aria-busy and stay in place.
  • Toasts announce through a polite live region; failures use role="alert".
  • Skeleton regions are aria-busy="true" with the skeleton hidden.
  • Spinners keep turning under reduced motion; shimmer stops.

Content

  • Busy labels end in an ellipsis.
  • Results name the value: "Resistance set to 20".

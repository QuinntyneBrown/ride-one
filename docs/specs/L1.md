# L1 - High-Level Requirements

These requirements were derived from the existing Python/aiohttp prototype (`echelon_server.py`) and its single-page UI (`index.html`). The target implementation is an **ASP.NET Core (.NET) backend** and an **Angular frontend**. Behaviour from the prototype is preserved unless a requirement states otherwise.

## L1-001: Bike discovery and connection
The system must automatically find the nearby Echelon bike over Bluetooth Low Energy, connect to it, keep the connection alive, and recover from disconnects and errors without user intervention.

## L1-002: Telemetry decoding
The system must decode the bike's notification packets into live metrics: cadence, speed (derived from cadence) and current resistance level, from which it must estimate power and the ride's average power, distance and energy, labelled as estimates.

## L1-003: Resistance control
The system must let the rider set the bike's resistance level, including overriding a running plan until its next segment, must report both the requested (target) value and the value the bike actually reports, and must log each command with its source and acknowledgement.

## L1-004: Interval workout engine
The system must run finite workout plans (HIIT intervals with an optional warm-up and cool-down, configurable interval sets where every set, the warm-up and the cool-down has its own durations, levels and cadence aims, or one flat level) made of segments, setting the bike's resistance automatically for each segment, letting the rider pause and resume, and handling the bike disconnecting and shutting off.

## L1-005: Real-time state API
The backend must expose the full live state through an HTTP API, including a push stream that delivers every state change to connected UIs in real time, and endpoints to control resistance and workouts.

## L1-006: Live metrics dashboard
The frontend must show the rider the connection status, live estimated power against the plan's target, cadence, speed and resistance, the ride's totals, the commands sent to the bike, notifications about the connection and commands, and controls for changing resistance.

## L1-007: Workout visualisation and cues
The frontend must show the active workout as a countdown of the current segment with its phase, the ride's elapsed and total time, a trace of power against the plan, optionally a YouTube video the rider rides along to, played in step with the ride clock, and visual and optional audio cues at segment changes and in the final seconds of each segment. It must also let the rider set up (by building a plan or by choosing a class, L1-014), start, pause, resume, end and replace workouts.

## L1-008: Diagnostics and observability
The system must record raw Bluetooth packets, keep a persisted snapshot of the latest state, track how long live data has been on screen, produce structured logs, and show a diagnostics view for troubleshooting.

## L1-009: Security
The system must protect the bike-control API from unauthorised use, validate all input, and avoid exposing the service beyond what the deployment needs. The UI loads nothing from other origins except the YouTube player for a ride-along video and the YouTube thumbnails shown as class covers (ADR 0012).

## L1-010: Performance and reliability
The system must deliver live data to the screen with low latency, use resources efficiently over long rides, and keep running through bike, Bluetooth and browser-connection failures.

## L1-011: Responsive and accessible UI
The frontend must work on every viewport size from phone to large desktop, and must be usable with a keyboard, screen readers and reduced-motion settings.

## L1-012: Platform and technology
The backend must be built on .NET and the frontend on Angular, with the Bluetooth layer isolated behind an abstraction so the system can run on Windows, Linux and macOS.

## L1-013: Treadmill support
Removed: bike only, ADR 0016.

## L1-014: Class library
The system must keep a configurable catalogue of classes, each a bike ride plan (warm-up, intervals or a steady level, cool-down, levels and cadence aims) together with the YouTube video it follows and the point in that video where the ride starts, grouped onto shelves that the catalogue defines. Classes are data, not code: the catalogue is a file the owner edits without rebuilding Wattzup (ADR 0014). The rider must be able to browse the classes by their video covers, open one to see its plan, and ride it with its configuration, changing its levels for that ride only.

## L1-015: Ride history
The system must record each finished or ended ride as a session (what was ridden, how it went and when), keep the sessions across restarts of the backend and the browser, and let the rider review one session and their progress over time: what changed on a class ridden again, the streak of days ridden, a weekly goal and achievements. Only real rides are shown; nothing is invented.

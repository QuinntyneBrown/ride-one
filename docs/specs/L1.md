# L1 - High-Level Requirements

These requirements were derived from the existing Python/aiohttp prototype (`echelon_server.py`) and its single-page UI (`index.html`). The target implementation is an **ASP.NET Core (.NET) backend** and an **Angular frontend**. Behaviour from the prototype is preserved unless a requirement states otherwise.

## L1-001: Bike discovery and connection
The system must automatically find a nearby Echelon bike over Bluetooth Low Energy, connect to it, keep the connection alive, and recover from disconnects and errors without user intervention.

## L1-002: Telemetry decoding
The system must decode the bike's notification packets into live riding metrics: cadence, speed (derived from cadence), and current resistance level, and must estimate power and the ride's average power, distance and energy from them, labelled as estimates.

## L1-003: Resistance control
The system must let the rider set the bike's resistance level, including overriding a running plan until its next segment, must report both the requested (target) level and the level the bike actually reports, and must log each resistance command with its source and acknowledgement.

## L1-004: Interval workout engine
The system must run finite workout plans (HIIT intervals with an optional warm-up and cool-down, or one flat level) made of segments, setting the bike's resistance automatically for each segment, letting the rider pause and resume, and handling the bike disconnecting and shutting off.

## L1-005: Real-time state API
The backend must expose the full live state through an HTTP API, including a push stream that delivers every state change to connected UIs in real time, and endpoints to control resistance and workouts.

## L1-006: Live metrics dashboard
The frontend must show the rider the connection status, live estimated power against the plan's target, cadence, speed, resistance, the ride's totals, the commands sent to the bike, notifications about the connection and commands, and controls for changing resistance.

## L1-007: Workout visualisation and cues
The frontend must show the active workout as a countdown of the current segment with its phase, the ride's elapsed and total time, a trace of power against the plan, and visual and optional audio cues at segment changes and in the final seconds of each segment. It must also let the rider set up, start, pause, resume, end and replace workouts.

## L1-008: Diagnostics and observability
The system must record raw Bluetooth packets, keep a persisted snapshot of the latest state, track how long live data has been on screen, produce structured logs, and show a diagnostics view for troubleshooting.

## L1-009: Security
The system must protect the bike-control API from unauthorised use, validate all input, and avoid exposing the service beyond what the deployment needs.

## L1-010: Performance and reliability
The system must deliver live data to the screen with low latency, use resources efficiently over long rides, and keep running through bike, Bluetooth and browser-connection failures.

## L1-011: Responsive and accessible UI
The frontend must work on every viewport size from phone to large desktop, and must be usable with a keyboard, screen readers and reduced-motion settings.

## L1-012: Platform and technology
The backend must be built on .NET and the frontend on Angular, with the Bluetooth layer isolated behind an abstraction so the system can run on Windows, Linux and macOS.

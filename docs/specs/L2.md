# L2 - Detailed Requirements

Protocol constants used throughout (taken from the prototype):

| Name                    | Value                                  |
| ----------------------- | -------------------------------------- |
| Service UUID            | `0bf669f1-45f2-11e7-9598-0800200c9a66` |
| Write characteristic    | `0bf669f2-45f2-11e7-9598-0800200c9a66` |
| Notify characteristic   | `0bf669f4-45f2-11e7-9598-0800200c9a66` |
| Init: device info       | `F0 A1 00 91`                          |
| Init: resistance range  | `F0 A3 00 93`                          |
| Init: start data stream | `F0 B0 01 01 A2`                       |
| Keepalive               | `F0 A0 01 01 92`                       |
| Set resistance          | `F0 B1 01 <level> <checksum>`          |
| Checksum                | sum of all preceding bytes `& 0xFF`    |
| km/h per rpm            | `0.37497622`                           |
| km per mile             | `1.609344`                             |
| Resistance range        | 1–32                                   |

Wattzup supports the Echelon bike only (ADR 0016). The treadmill requirements, L2-062 to L2-075,
are removed; their IDs are kept so the others keep theirs.

Wattzup runs entirely in the rider's browser, with no Wattzup server (ADR 0019). The requirements
that only concerned the former .NET server (L2-015, L2-030 to L2-037, L2-039, L2-042, L2-043,
L2-055 and L2-057) are removed, and their IDs are not reused. A criterion marked _Removed_ keeps
its number so the others keep theirs. The _contracts_ named below are the TypeScript interfaces in
`@wattzup/api` (`BIKE_API`, `WORKOUT_API`, `CLASS_API`, `SESSION_API` and others) that every screen
depends on; `@wattzup/browser` implements each of them in the page. A contract that refuses a call
rejects with a `ContractError` (`@wattzup/api`) carrying a `code` the screens branch on and, for a plan, per-field `errors`.

## L2-001: Bike identification

**Traces to:** L1-001

_(Changed: Wattzup no longer scans in the background; the rider picks the bike in the browser's device chooser, L2-090.)_ A device is an Echelon bike when its advertised name starts with `ECH` (case-insensitive) or its advertised service UUIDs include the Echelon service UUID (case-insensitive). The chooser's filters (L2-090) and the bikes the browser remembers are matched by this rule.

**Acceptance Criteria:**

1. Removed: background scanning, ADR 0019.
2. Given a device advertising the name `ECHEX-3-141844`, then it is an Echelon bike.
3. Given a device named `echex-3` (lowercase), then it is an Echelon bike.
4. Given a device with no name that advertises the Echelon service UUID in upper case, then it is an Echelon bike.
5. Given a device named `Peloton` that does not advertise the Echelon service, then it is not an Echelon bike.
6. Removed: background scanning, ADR 0019.

## L2-002: Connection and initialisation

**Traces to:** L1-001

Once the rider has picked the bike (L2-090), Wattzup must connect, subscribe to the notify characteristic, then send the three init commands in order with write-with-response, 300 ms apart. Writes to the bike go one at a time: init commands, keepalives and resistance commands queue rather than overlap.

**Acceptance Criteria:**

1. Given a device is selected, when connection starts, then `ble` is `connecting` and `device` is the device name, or its address if it has no name.
2. Given the connection succeeds, when it is established, then `ble` is `connected` and the change is published to the live state (L2-093).
3. Given the connection is established, when initialisation runs, then notifications are subscribed before any init command is written.
4. Given initialisation runs, then the commands device info, resistance range and start data stream are written in that order, each with response, with at least 300 ms between writes.

---

## L2-003: Keepalive

**Traces to:** L1-001

While connected, Wattzup must write the keepalive command once per second, timed from the clock rather than counted ticks (L2-091).

**Acceptance Criteria:**

1. Given the bike is connected and initialised, when 5 seconds pass, then between 4 and 6 keepalive writes have been sent, each with response.
2. Removed: displayed time was the server's measure, ADR 0019.

---

## L2-004: Disconnect and error recovery

**Traces to:** L1-001

Wattzup must recover automatically from disconnects and from any Web Bluetooth error, by reconnecting to the bike the rider picked, without opening the chooser again.

**Acceptance Criteria:**

1. Given the bike is connected, when it disconnects (`gattserverdisconnected`), then `ble` becomes `disconnected`, a running workout waits as L2-013, and Wattzup retries the connection to the same bike every 3 s without the chooser until it connects or the rider ends the ride.
2. Given any Web Bluetooth error, when it occurs, then `ble` is `error`, `error` is `<error name>: <message>`, rendered as text, and the retry of criterion 1 starts after 3 s.
3. Given repeated failures, when Wattzup has been open for 1 hour with the bike off, then it is still retrying.
4. Given the bike is off, when it is switched on and pedalled, then Wattzup connects within one retry without a reload.
5. Given `ble` is not `connected` or `connecting`, when the rider presses **Reconnect** (`BIKE_API.reconnect()`), then the pending retry is cancelled and a connection attempt to the same bike starts at once; given `ble` is `connected` or `connecting`, the call is refused with `code` `already_connected`; given the reconnect fails, a danger toast reads `The bike didn't answer. Wake it with a pedal stroke, then try again.`

## L2-005: Packet framing and counting

**Traces to:** L1-002

Every notification must be counted and logged; only well-formed packets are decoded.

**Acceptance Criteria:**

1. Given any notification, when it is received, then `packets` increases by 1, even if the packet is later ignored.
2. Given a packet shorter than 4 bytes, when it is received, then no metric changes.
3. Given a packet whose first byte is not `0xF0`, when it is received, then no metric changes.
4. Given a packet of an unknown type (e.g. `F0 D0 01 01 C2`), when it is received, then no metric changes and no error is raised.

---

## L2-006: Resistance packet decoding

**Traces to:** L1-002

A packet with type byte `0xD2` must set `resistance` to byte index 3.

**Acceptance Criteria:**

1. Given packet `F0 D2 01 0C CF`, when it is decoded, then `resistance` is 12.
2. Given a resistance packet is decoded, then `last_data_at` is set to the current time, `first_data_at` is set if it was `null`, and the state is published.

---

## L2-007: Workout data decoding

**Traces to:** L1-002

A packet with type byte `0xD1` and at least 13 bytes must set cadence to the big-endian 16-bit value at bytes 9–10, and derive speed from it. `speed_kmh` = round(cadence × 0.37497622, 1). `speed_mph` = round(cadence × 0.37497622 ÷ 1.609344, 1), computed from the unrounded km/h value.

**Acceptance Criteria:**

1. Given packet `F0 D1 09 00 05 00 00 00 00 00 50 00 1F` (bytes 9–10 = `00 50`), when it is decoded, then `cadence` is 80, `speed_kmh` is 30.0 and `speed_mph` is 18.6.
2. Given bytes 9–10 are `01 00`, when decoded, then `cadence` is 256.
3. Given cadence 0, when decoded, then `speed_kmh` and `speed_mph` are both 0.0.
4. Given a `0xD1` packet of 12 bytes, when received, then no metric changes.
5. Given a workout packet is decoded, then `last_data_at`/`first_data_at` are updated as in L2-006 and the state is published.

---

## L2-008: Set resistance command

**Traces to:** L1-003

Wattzup must build the set-resistance command `F0 B1 01 <level> <checksum>` and write it with response.

**Acceptance Criteria:**

1. Given level 12, when the command is built, then the bytes are `F0 B1 01 0C AE`.
2. Given level 32, when the command is built, then the bytes are `F0 B1 01 20 C2`.
3. Given the bike is connected, when a resistance of 12 is sent, then `target_resistance` becomes 12 and the state is published.
4. Given the bike is not connected, when a resistance send is attempted, then nothing is written and the send reports failure.

---

## L2-009: Target vs. actual resistance

**Traces to:** L1-003

The state must carry `target_resistance` (last requested) separately from `resistance` (last reported by the bike).

**Acceptance Criteria:**

1. Given `target_resistance` is 20 and the bike still reports 12, when state is read, then `target_resistance` is 20 and `resistance` is 12.
2. Given the bike then reports 20, when state is read, then both are 20.

## L2-010: Workout plan definition and validation

**Traces to:** L1-004

_(Changed: the design's finite plans replace the prototype's list of steps repeated in cycles; see ADR 0002. Changed again: a third kind, `intervals`, makes every set, the warm-up and the cool-down configurable.)_ A workout is defined by a plan of one of three kinds, given to `WORKOUT_API.start` as an object with snake_case fields, and validated by the same rules wherever it comes from (setup, a class, an imported session):

| Kind        | Fields                             | Allowed values                                                                                                                |
| ----------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `hiit`      | `rounds`                           | integer 1–30                                                                                                                  |
|             | `work_seconds`, `rest_seconds`     | integer 5–3600                                                                                                                |
|             | `work_level`, `rest_level`         | integer 1–32                                                                                                                  |
|             | `warmup`, `cooldown`               | boolean (a warm-up lasts 180 s, a cool-down 120 s)                                                                            |
| `flat`      | `level`                            | integer 1–32                                                                                                                  |
|             | `minutes`                          | integer 1–180                                                                                                                 |
|             | `cadence`                          | integer 40–150 (the rider's cadence goal, rpm)                                                                                |
| `intervals` | `warmup`, `cooldown`               | `null` (off) or `{seconds, level, cadence}`: `seconds` integer 60–1800, `level` 1–32, `cadence` 40–150 (the cadence aim, rpm) |
|             | `sets`                             | array of 1–10 sets, in ride order                                                                                             |
|             | set `rounds`                       | integer 1–30; the rounds of all sets add up to at most 30                                                                     |
|             | set `work_seconds`                 | integer 5–3600                                                                                                                |
|             | set `rest_seconds`                 | integer 0 or 5–3600; 0 means the set's efforts have no recover                                                                |
|             | set `work_level`, `rest_level`     | integer 1–32                                                                                                                  |
|             | set `work_cadence`, `rest_cadence` | integer 40–150 (cadence aims, rpm)                                                                                            |

An `intervals` ride (warm-up, every set's rounds, cool-down) lasts at most 180 minutes.

_(New: video ride-along, L2-076, ADR 0012.)_ Every plan kind may carry `video`:

| Field                 | Allowed values                                                                                                                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `video`               | absent or `null` (no video), or `{url, start_seconds}`                                                                                                                                                                                                 |
| `video.url`           | a YouTube link: `youtube.com/watch?v=<id>`, `youtu.be/<id>`, `youtube.com/shorts/<id>` or `youtube.com/embed/<id>`, with or without `https://`, `www.` or `m.`, where `<id>` is 11 characters of `A–Z a–z 0–9 _ -`; other query parameters are ignored |
| `video.start_seconds` | number 0–43200 in steps of 0.1: the point in the video that lines up with the ride's 0:00                                                                                                                                                              |

Wattzup keeps only the video id and the start point; it never fetches the link.

**Acceptance Criteria:**

1. Given `{"kind":"hiit","rounds":8,"work_seconds":40,"rest_seconds":20,"work_level":18,"rest_level":6,"warmup":true,"cooldown":true}`, when submitted, then the plan is accepted.
2. Given `{"kind":"flat","level":12,"minutes":30,"cadence":85}`, when submitted, then the plan is accepted.
3. Given `rounds` 0 or 31, when submitted, then it is rejected and the field `rounds` is named with the message `Enter 1 to 30 rounds.`
4. Given `rest_seconds` 4, when submitted, then it is rejected and the field `rest_seconds` is named with the message `Recover must be at least 0:05.`; given `work_seconds` 4, the message is `Work must be at least 0:05.`
5. Given a level of 0 or 33 in any level field, when submitted, then it is rejected naming that field with `Level must be 1 to 32.`
6. Given `minutes` 0 or 181, when submitted, then it is rejected naming `minutes` with `Enter 1 to 180 minutes.`; given `cadence` 39 or 151, it names `cadence` with `Cadence goal must be 40 to 150 rpm.`
7. Given an unknown `kind`, a missing field, a non-integer number or a non-boolean switch, when submitted, then it is rejected and no workout is started; the field is named with `Choose HIIT, Intervals or Flat.` (`kind`), `Enter a whole number.` (a missing or mistyped number) or `Choose on or off.` (a missing or mistyped switch).
8. Given any rejection, then it is a `ContractError` with `code` = `invalid_workout` and an `errors` map from field name to messages.
9. Given `work_seconds` or `rest_seconds` over 3600, when submitted, then it is rejected naming the field with `Work must be at most 60:00.` or `Recover must be at most 60:00.`
10. Given a plan that is not an object (for example a stored draft that is not valid JSON), when submitted, then it is rejected with `code` = `invalid_workout` and `errors` `{"body":["The request body is not valid JSON."]}`.
11. Given `{"kind":"intervals","warmup":{"seconds":300,"level":14,"cadence":80},"sets":[{"rounds":1,"work_seconds":30,"work_level":24,"work_cadence":100,"rest_seconds":180,"rest_level":8,"rest_cadence":72},{"rounds":2,…,"rest_seconds":150,…},{"rounds":2,…,"rest_seconds":120,…},{"rounds":2,…,"rest_seconds":90,…},{"rounds":1,…,"rest_seconds":0,…}],"cooldown":{"seconds":360,"level":6,"cadence":70}}` (every elided field as in the first set; the _Descending recoveries_ plan), when submitted, then the plan is accepted; `warmup` or `cooldown` `null` is accepted too.
12. Given an `intervals` plan, then a failing field inside it is named by its path, `warmup.seconds`, `cooldown.level` or `sets[<i>].<field>` with `i` from 0, with these messages: `sets` missing, not an array, empty or longer than 10, `Enter 1 to 10 sets.`; a set's `rounds` outside 1–30, `Enter 1 to 30 rounds.`; `work_seconds` and the levels as criteria 4, 5 and 9; `rest_seconds` 1–4, `Recover must be 0 (none) or at least 0:05.`, over 3600, `Recover must be at most 60:00.`; a cadence aim outside 40–150, `Cadence aim must be 40 to 150 rpm.`; warm-up `seconds` outside 60–1800, `Warm-up must be 1:00 to 30:00.` (`Cool-down must be 1:00 to 30:00.` for the cool-down); `warmup` or `cooldown` neither `null` nor an object, `Choose on or off.`
13. Given an `intervals` plan whose sets' rounds add up to more than 30, then `sets` is named with `At most 30 efforts in a plan.`; given one longer than 180 minutes, then `sets` is named with `A ride can be at most 180 minutes.`
14. Given any valid plan with `"video":{"url":"https://www.youtube.com/watch?v=QUoToFsMNig","start_seconds":12}`, when submitted, then it is accepted and the workout reports `plan.video` `{"video_id":"QUoToFsMNig","start_seconds":12.0}` (L2-014); the same holds for `youtu.be/QUoToFsMNig`, `m.youtube.com/watch?v=QUoToFsMNig&t=40`, `youtube.com/shorts/QUoToFsMNig` and `www.youtube.com/embed/QUoToFsMNig`.
15. Given `video` absent or `null`, when submitted, then it is accepted and the workout reports `plan.video` `null`.
16. Given `video.url` that is not one of those forms (e.g. `https://vimeo.com/76979871`, `https://www.youtube.com/watch?v=short`, `javascript:alert(1)`, or a link over 2048 characters), when submitted, then it is rejected naming `video.url` with `That doesn't look like a YouTube link.`
17. Given `video.start_seconds` below 0, above 43200 or not a number, when submitted, then it is rejected naming `video.start_seconds` with `Start point must be 0:00 to 12:00:00.`; a value with more than one decimal place is rounded to 0.1.

## L2-011: Workout execution

**Traces to:** L1-004

_(Changed: the plan is finite; it no longer loops.)_ The engine must advance the ride one second at a time while the workout is `running`, tracking `elapsed_seconds` from 0 to `total_seconds` and the current `segment` and its `remaining` seconds.

**Acceptance Criteria:**

1. Given a workout starts, then `workout` holds the plan, its `segments`, `segment` 0, `elapsed_seconds` 0, `total_seconds`, `remaining` equal to segment 0's duration, `mode` `plan`, `summary` (L2-060) and `status`.
2. Given the workout is `running`, when 1 second passes, then `elapsed_seconds` increases by 1, `remaining` decreases by 1, and the state is published.
3. Given `remaining` reaches 0 on a segment that is not the last, when the next tick runs, then `segment` increases by 1 and `remaining` is that segment's duration.
4. Given `elapsed_seconds` reaches `total_seconds`, then `status` is `ended`, ticking stops, and the bike is left at the last segment's level.

## L2-012: Automatic resistance during workouts

**Traces to:** L1-004

_(Changed from the prototype's per-step resend; the 5-second resend rule is kept.)_ While `mode` is `plan`, the engine must set the bike to the current segment's level.

**Acceptance Criteria:**

1. Given a segment starts, when its first tick runs, then the segment's level is sent once with source `plan`.
2. Given the bike reports a resistance different from the level last sent, when `remaining` is a multiple of 5, then that level is sent again.
3. Given the bike reports the level last sent, when ticks run, then no further sends happen for that segment.
4. Given a send fails, then `error` is `set resistance failed: <message>`, the command is logged as `failed` (L2-048), and the workout keeps running.
5. Given the bike reconnects after a pause, when the next tick runs, then the current segment's level is sent again.
6. Given `mode` is `manual` (L2-047), then the engine sends no plan level until the mode returns to `plan`, and the resend of criterion 2 applies to the manual level instead.

## L2-013: Waiting, disconnect, shutdown and replacement

**Traces to:** L1-004

_(The 90-second shut-off rule is kept from the prototype.)_

**Acceptance Criteria:**

1. Given a workout starts while the bike is not connected, then `status` is `waiting for bike`, `elapsed_seconds` and `remaining` do not change, and the ride starts at 0:00 as soon as the bike connects.
2. Given the workout is running and the bike disconnects, then `status` is `paused: bike disconnected` and `elapsed_seconds` and `remaining` do not change.
3. Given the bike has been disconnected for more than 90 seconds during a started ride, then `status` is `ended: bike shut off`, `ended_reason` is `bike shut off`, and the workout stops ticking.
4. Given the bike reconnects within 90 seconds, then the workout resumes from the same `segment` and `remaining`, and the segment's level is sent again (L2-012).
5. Given a workout is active, when a new workout is started, then the old one stops and the new one starts at segment 0 with `elapsed_seconds` 0 and fresh ride totals.
6. Given a workout is active, when it is stopped, then `status` is `stopped`, ticking stops, the bike is left at its current level, and the state is published.

## L2-014: State model contract

**Traces to:** L1-005

The live state keeps the prototype's snake_case field names so the contract stays stable, and adds the fields the design needs. Its type, `BikeState`, and the types of every contract are kept by hand in `frontend/projects/api/src/contract/schema.d.ts`; no other file declares them. _(Changed: `workout` now describes a finite plan; `cycle` and `steps` are removed; the fields from `adapter` on are new. Changed again for ADR 0019: `ui_clients`, `transport`, `exposed` and `bind_address`, which described the server, are removed.)_

| Field               | Type           | Notes                                                                                |
| ------------------- | -------------- | ------------------------------------------------------------------------------------ |
| `ble`               | string         | `starting` \| `scanning` \| `connecting` \| `connected` \| `disconnected` \| `error` |
| `device`            | string \| null | advertised name of the bike the rider picked                                         |
| `device_label`      | string \| null | the display name of the bike: `device`                                               |
| `error`             | string \| null |                                                                                      |
| `resistance`        | int \| null    | last reported by the bike                                                            |
| `target_resistance` | int \| null    | last requested                                                                       |
| `workout`           | object \| null | see below                                                                            |
| `cadence`           | int \| null    | rpm                                                                                  |
| `speed_kmh`         | number \| null | 1 decimal                                                                            |
| `speed_mph`         | number \| null | 1 decimal                                                                            |
| `packets`           | int            |                                                                                      |
| `first_data_at`     | number \| null | Unix epoch seconds                                                                   |
| `last_data_at`      | number \| null | Unix epoch seconds                                                                   |
| `displayed_since`   | number \| null | always `null` (displayed time was the server's measure, ADR 0019)                    |
| `displayed_seconds` | number         | always 0                                                                             |
| `adapter`           | string         | `unknown` \| `on` \| `off`, from `navigator.bluetooth.getAvailability()` (L2-089)    |
| `simulated`         | bool           | true when opened with `?simulate` in a development build (L2-099)                    |
| `connection_id`     | string         | first 8 hex digits of the service UUID, `0bf669f1`, once a bike is picked            |
| `power`             | int \| null    | estimated watts (L2-049)                                                             |
| `target_power`      | int \| null    | estimated target watts for the current segment                                       |
| `avg_power`         | int \| null    | ride average, watts                                                                  |
| `distance_km`       | number \| null | ride distance, 2 decimals                                                            |
| `kcal`              | int \| null    | ride energy, estimated (L2-049)                                                      |
| `heart_rate`        | int \| null    | always `null`; no heart-rate source exists (ADR 0003)                                |
| `commands`          | array          | the last 5 commands, newest first (L2-048)                                           |

`workout` is `{plan, summary, segments:[{kind, start, duration, level, cadence, round}], segment:int, remaining:int, elapsed_seconds:int, total_seconds:int, mode:"plan"|"manual", plan_level:int|null, status:string, ended_reason:string|null, session_id:string|null, class_id:string|null}`. `session_id` is the id of the session the ride was saved as (L2-081), set once the ride has ended and been saved, else `null`. `class_id` is the class the workout was started from (L2-081 criterion 7), else `null` (L2-102 criterion 5). `status` is one of `waiting for bike`, `running`, `paused`, `paused: bike disconnected`, `ended`, `ended: bike shut off`, `stopped`. The status strings are contract identifiers. Each command entry is `{at, ride_seconds, level, source, status, ack_ms}` (L2-048). `workout.plan` is the validated plan (L2-010) with `video` reported as `{video_id:string, start_seconds:number}` or `null`, never the submitted link (L2-076, ADR 0012).

**Acceptance Criteria:**

1. Given Wattzup has just loaded and no bike has been picked, when the live state is read, then `ble` is `disconnected`, `packets` = 0, `displayed_seconds` = 0, `commands` = `[]`, `adapter` = `unknown`, and all nullable fields `null`.
2. Given any state, then every field above is present with the stated name and type, and nulls are written as `null` rather than left out (so an exported session or state reads the same in every version).
3. Given the contract types, then every contract, implementation and screen uses those of `schema.d.ts`; none is redeclared elsewhere.

## L2-016: Resistance contract

**Traces to:** L1-005

_(Changed: the `POST /api/resistance` endpoint became a call on the `BIKE_API` contract, ADR 0019.)_ `BIKE_API.setResistance(level)` sets the bike's resistance.

**Acceptance Criteria:**

1. Given the bike is connected and level 12, when called, then level 12 is written to the bike (L2-008) and the call resolves.
2. Given level 0, 33 or a non-integer, when called, then it is refused with `code` `invalid_level` and nothing is written.
3. Given the bike is not connected, when called with a valid level, then it is refused with `code` `bike_not_connected`; given the write fails, it is refused with `code` `send_failed` and `error` is `set resistance failed: <message>`.

---

## L2-017: Workout contract

**Traces to:** L1-005

_(Changed for finite plans. Changed again: the `/api/workout` endpoints became calls on the `WORKOUT_API` contract, ADR 0019.)_ `WORKOUT_API` offers `start(plan)` (L2-010), `stop()`, `pause()`, `resume()`, `backToPlan()` and `trace()` (L2-050).

**Acceptance Criteria:**

1. Given a valid plan, when `start` is called, then the workout starts, whether or not the bike is connected (L2-013), and the call resolves with the new workout.
2. Given an invalid plan, when `start` is called, then it is refused as in L2-010.
3. Given any state, when `stop` is called, then the call resolves with the saved session's id, or `null` when none was saved (L2-081).
4. Given no workout exists, when `stop` is called, then it still resolves (with `null`) and `workout` stays `null`.
5. Given `pause`, `resume` or `backToPlan` is called with no active workout, then it is refused with `code` = `no_active_workout`.

## L2-018: Connection status line

**Traces to:** L1-006

_(Changed: the design's status line replaces the coloured pill. Changed again: the server-offline row is gone and the rows for a browser without Bluetooth and for no bike picked are added, ADR 0019.)_ The app bar must show an icon, a name and a state label for the connection.

| Condition                                              | Name                             | State                         | Icon                                      |
| ------------------------------------------------------ | -------------------------------- | ----------------------------- | ----------------------------------------- |
| Bluetooth unavailable in this browser or page (L2-089) | `Bluetooth`                      | `Unavailable in this browser` | bluetooth-off                             |
| `adapter` `off`                                        | `Bluetooth`                      | `Off`                         | bluetooth-off                             |
| no bike picked (`ble` `disconnected`, `device` `null`) | `No bike connected`              | none                          | bluetooth-off                             |
| `ble` `connected`                                      | `device_label`                   | `Connected`                   | bluetooth                                 |
| `ble` `scanning` or `starting`                         | `Echelon bike`                   | `Scanning…`                   | bluetooth, animated unless reduced motion |
| `ble` `connecting`                                     | `device_label`                   | `Connecting…`                 | bluetooth                                 |
| `ble` `disconnected`                                   | `device_label` or `Echelon bike` | `Disconnected`                | bluetooth-off                             |
| `ble` `error`, adapter not off                         | `Bike status`                    | `Error`                       | bluetooth-off                             |
| no state yet                                           | `Bike status`                    | `Unknown`                     | bluetooth                                 |

**Acceptance Criteria:**

1. Given `ble` `connected` and `device_label` `Echelon EX-5s`, then the status line reads `Echelon EX-5s` `Connected`.

1. Given `cadence` 95 and `resistance` 18, then `power` = max(0, round(95 × (0.55 + 18 × 0.155))) = 317.
2. Given `cadence` or `resistance` is `null`, then `power` is `null`.
3. Given a `running` workout whose segment has cadence aim 100 and level 18, then `target_power` is 334; with no running workout it is `null`.
4. Given each running tick, then the tick's `power` (0 if `null`) is added to the ride average, and `speed_kmh` ÷ 3600 is added to `distance_km`.
5. Given `avg_power` 208 after 760 running seconds, then `kcal` = round(208 × 760 ÷ 1000 ÷ 0.24 ÷ 4.184) = 157.
6. Given a new workout starts, then `avg_power`, `distance_km` and `kcal` reset to 0; given a workout ends or stops, they keep their final values.
7. Given `heart_rate`, then it is always `null`.

## L2-077: Class catalogue

**Traces to:** L1-014

_(New: from the 2026-11-17 Magic Patterns frames Video Library and Video Workout; ADR 0014.)_ A class is a bike plan with the YouTube video it follows. The catalogue of classes is a JSON file, `classes.json`, published beside `index.html` (L2-096); nothing in the code lists a class. A GCN class's levels follow the video's effort scale: effort _e_/10 is level 8 + 1.6 × _e_, rounded (1/10 is level 10, 10/10 is level 24).

| Field                    | Rule                                                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `shelves`                | array of 0–20 `{id, title, tagline}`, in display order                                                             |
| `classes`                | array of 0–200 `{id, title, channel, focus, description, shelf, plan}`, in display order                           |
| `id` (shelf and class)   | 1–64 characters of `a–z 0–9 -`, unique among the shelves or among the classes                                      |
| `title`                  | 1–80 characters                                                                                                    |
| `channel`, `focus`       | 1–40 characters (`GCN Training`, `HIIT`)                                                                           |
| `tagline`, `description` | 0–280 characters                                                                                                   |
| `shelf`                  | the `id` of a shelf in the file                                                                                    |
| `plan`                   | a bike plan as L2-010 (`hiit`, `intervals` or `flat` with a level), optionally with `video` `{url, start_seconds}` |

**Acceptance Criteria:**

1. Given a catalogue file of valid shelves and classes, when it is read, then every shelf and class is offered by L2-078 in file order.

7. Given the owner replaces the file, then the next load of Wattzup reads the new catalogue, and a ride in progress is not affected.
8. Given a class's `plan.video`, then only its video id and start point are kept, as L2-010 criterion 14; Wattzup never fetches the link or the video.
9. Given any text field, then it is kept as plain text and rendered as text, never as HTML (L2-097 criterion 4).

## L2-081: Session record

**Traces to:** L1-015

_(New: from the Magic Patterns frames Ride Dashboard (`End` builds a session record) and Session Summary, and the rules of the OS file `shared/sessions.ts`; ADR 0015.)_ A _session_ is a saved ride. When a workout ends, the workout engine builds the session from the samples the workout engine took each running second (power and cadence as the bike reported them, a missing value counting as 0) and saves it (L2-082). Heart rate is not recorded: Wattzup has no heart-rate sensor (ADR 0003).

A session is `{id, ended_at, class_id, title, plan, segments, planned_seconds, ridden_seconds, completed, avg_power, max_power, best_minute_power, avg_cadence, distance_km, kcal, on_target_pct, dips:[{start, duration, target, low, kind, round}], power_trace, cadence_trace}`:

| Field                               | Rule                                                                                                                                                                                                                                  |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                | 12 characters of `a–f 0–9`, unique among the sessions                                                                                                                                                                                 |
| `ended_at`                          | the UTC time the workout ended (ISO 8601)                                                                                                                                                                                             |
| `class_id`, `title`                 | the class's `id` and `title` when the ride was started with `class_id` (criterion 7); otherwise `null` and `workout.summary` (L2-060)                                                                                                 |
| `plan`, `segments`                  | `workout.plan` and `workout.segments` as L2-014 carries them                                                                                                                                                                          |
| `planned_seconds`, `ridden_seconds` | the plan's total and the running seconds ridden (`elapsed_seconds`)                                                                                                                                                                   |
| `completed`                         | `ridden_seconds ≥ planned_seconds − 5`                                                                                                                                                                                                |
| `avg_power`, `max_power`            | the mean and the highest estimated power of the running seconds, W, whole (ADR 0003); `avg_power` equals the dashboard's `avg_power` at the end                                                                                       |
| `best_minute_power`                 | the highest mean of 60 consecutive running seconds of power, W, whole                                                                                                                                                                 |
| `avg_cadence`                       | the mean cadence of the running seconds, rpm, whole                                                                                                                                                                                   |
| `distance_km`, `kcal`               | the ride's `distance_km` (2 decimals) and `kcal` at the end (L2-049)                                                                                                                                                                  |
| `on_target_pct`                     | of the seconds in counted segments (table below), the share not under target, 0–100 whole; 100 when no segment counts                                                                                                                 |
| `dips`                              | every run of at least 6 consecutive seconds under target within one counted segment: `start` (ride second), `duration` (s), `target` (the segment's cadence aim), `low` (the lowest cadence in it), `kind` and `round` of the segment |
| `power_trace`, `cadence_trace`      | means of each 5 running seconds, whole, oldest first; the last holds the remaining 1–5 seconds                                                                                                                                        |

A second is _under target_ when its cadence is below the segment's cadence aim by more than the segment kind's tolerance:

| Segment kind | Counted | Under target when cadence < |
| ------------ | ------- | --------------------------- |
| `warmup`     | no      | —                           |
| `cooldown`   | no      | —                           |
| `work`       | yes     | aim − 6 rpm                 |
| `steady`     | yes     | aim − 6 rpm                 |
| `rest`       | yes     | aim − 12 rpm                |

**Acceptance Criteria:**

1. Given a workout with at least 60 running seconds, when it is stopped (`WORKOUT_API.stop()`, L2-013), when it ends at the end of its plan (`ended`) or when the bike has been off for 90 s (`ended: bike shut off`, L2-058), then one session is saved with the fields of the table, and `workout.session_id` (L2-014) is its `id`.
2. Given a workout with fewer than 60 running seconds, or no workout, when the workout is stopped or ends, then no session is saved and `workout.session_id` stays `null`.
3. Removed: bike only, ADR 0016.
4. Given a ride ends `completed` false, then the session keeps the ridden part only: the traces, dips and averages cover `ridden_seconds`, and `planned_seconds` is the whole plan.
5. Given each row of the two tables, then the session's `on_target_pct`, `dips`, `best_minute_power` and `completed` follow it, each row proven by a unit test in `@wattzup/browser`.
6. Given a run under target that spans two segments, then it is two dips, one per segment, each kept only if it lasts at least 6 s.
7. Given `WORKOUT_API.start` (L2-010) with an optional `class_id` beside the plan, then a `class_id` that names a class in the catalogue (L2-077) is kept for the session with that class's `title`; one that names no class is refused with `code` `invalid_workout` and the field `class_id`; without it the session has `class_id` `null`.
8. Given `WORKOUT_API.stop()` resolves, then it answers the saved session's `id`, or `null` when none was saved.
9. Given a session, then it holds no heart rate and no Bluetooth device name.

## L2-087: Streaks, weekly goal, previous attempt, bests and achievements

**Traces to:** L1-015

_(New: from the rules of the OS file `shared/sessions.ts`; ADR 0015.)_ `@wattzup/browser` computes these from the saved sessions and the time now (its clock), in the browser's time zone. A _ridden day_ is a local date on which a session ended. A _finished attempt_ at a class is a `completed` session with that `class_id`; rides from `/setup` (`class_id` `null`) have no attempts, no previous attempt and no class best.

| Figure              | Rule                                                                                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `streak.rode_today` | today is a ridden day                                                                                                                                                  |
| `streak.current`    | the number of consecutive ridden days ending today when `rode_today`, else ending yesterday (a streak survives until the end of today); 0 when that day was not ridden |
| `streak.best`       | the longest run of consecutive ridden days ever, and never less than `current`                                                                                         |
| `week.rides`        | the sessions that ended since Monday 00:00 of this week (local); a week starts on Monday                                                                               |
| `week.goal`         | 4                                                                                                                                                                      |
| previous attempt    | the latest finished attempt at the same class that ended before this session; none for `class_id` `null`                                                               |

| Best (in this order)         | Set when                                                                                                                                |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `Best 1-minute power`        | at least one session ended before this one, and `best_minute_power` is higher than every earlier session's                              |
| `Best average on this class` | this session is a finished attempt, an earlier finished attempt at the class exists, and `avg_power` is higher than every earlier one's |
| `No cadence dips`            | this session is `completed`, has at least one `work` segment and has no dips                                                            |

| Achievement `id`   | Title            | Detail                                       | Value                                                  | Goal | Unit |
| ------------------ | ---------------- | -------------------------------------------- | ------------------------------------------------------ | ---- | ---- |
| `seven-straight`   | Seven straight   | Ride seven days in a row                     | `streak.best`                                          | 7    | days |
| `century`          | Century          | Ride 100 km in total                         | the sum of `distance_km`                               | 100  | km   |
| `long-hour`        | The long hour    | Finish five rides of an hour or more         | completed sessions with `planned_seconds` ≥ 3600       | 5    | —    |
| `interval-regular` | Interval regular | Finish eight interval rides                  | completed sessions whose plan is `hiit` or `intervals` | 8    | —    |
| `metronome`        | Metronome        | Hold cadence target 97% of a ride            | the highest `on_target_pct` of a completed session     | 97   | %    |
| `clean-sheet`      | Clean sheet      | Finish an interval ride with no cadence dips | completed sessions with a `work` segment and no dips   | 1    | —    |

The design's _Ladder regular_ (a named class) and the 60-minute tier of _The long hour_ are expressed by plan properties, because nothing in the code names a class (ADR 0014).

**Acceptance Criteria:**

1. Given each row of the three tables, then the figure follows it, proven by a unit test per row in `@wattzup/browser` with the time and the time zone fixed by the test, including: a session at 23:59 and one at 00:01 the next local day are two ridden days; ridden yesterday but not today keeps the streak; last ridden two days ago gives 0; two sessions on one day count one day but two rides this week; a session on Sunday is not in the week that starts on Monday.
2. Given an achievement, then `unlocked` is `value ≥ goal`, and the list is ordered unlocked first, then by `value ÷ goal` descending, then by the table's order.
3. Given no sessions, then `streak` is `{current:0, best:0, rode_today:false}`, `week.rides` 0, `totals` zero, `classes` `[]`, and every achievement has value 0 and is locked.
4. Given the figures, then none is ever invented: with no earlier session there is no previous attempt and no `Best 1-minute power`.

2. Given a tier, then the scene draws with exactly the techniques of the table whose _From tier_ is that tier or a lower one. A technique the table marks _not built_ is drawn at no tier. `ultra` is offered only with WebGPU.
3. Given World Ride opens, then the scene starts at `ultra` with WebGPU and at `high` with WebGL2.
4. Given the frame budget of 16.7 ms, then every 2 seconds the scene takes the median frame time of that window. After two windows in a row over 20 ms, it drops one tier. It never drops below `low`, and it never raises the tier again during the ride.
5. Given `prefers-reduced-motion: reduce`, then every technique marked _off_ is not drawn and every technique marked _still_ does not move on its own, at every tier. The tier is not changed by it.
6. Given a technique's captured or baked asset (meshes, scans, maps, lightmaps, probes, impostors, splats, texture pages) is missing, then the scene draws that part with the next lower tier's technique and shows no error. Every such asset is served from the same origin (L2-101 criterion 4).
7. Given any tier, then the HUD panels of L2-103 to L2-109 respond to input as at `low`; the scene's work never blocks them.

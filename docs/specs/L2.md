# L2 - Detailed Requirements

Protocol constants used throughout (taken from the prototype):

| Name | Value |
|---|---|
| Service UUID | `0bf669f1-45f2-11e7-9598-0800200c9a66` |
| Write characteristic | `0bf669f2-45f2-11e7-9598-0800200c9a66` |
| Notify characteristic | `0bf669f4-45f2-11e7-9598-0800200c9a66` |
| Init: device info | `F0 A1 00 91` |
| Init: resistance range | `F0 A3 00 93` |
| Init: start data stream | `F0 B0 01 01 A2` |
| Keepalive | `F0 A0 01 01 92` |
| Set resistance | `F0 B1 01 <level> <checksum>` |
| Checksum | sum of all preceding bytes `& 0xFF` |
| km/h per rpm | `0.37497622` |
| km per mile | `1.609344` |
| Resistance range | 1–32 |

## L2-001: Bike scanning
**Traces to:** L1-001

The backend must scan for BLE devices for up to 20 seconds per attempt and select the first device whose advertised name starts with `ECH` (case-insensitive) or whose advertised service UUIDs include the Echelon service UUID (case-insensitive).

**Acceptance Criteria:**
1. Given the scanner is running, when a scan starts, then `ble` is `scanning`, `error` is `null`, and the change is broadcast.
2. Given a device advertising the name `ECHEX-3-141844`, when it is discovered, then it is selected.
3. Given a device named `echex-3` (lowercase), when it is discovered, then it is selected.
4. Given a device with no name that advertises the Echelon service UUID in upper case, when it is discovered, then it is selected.
5. Given a device named `Peloton` that does not advertise the Echelon service, when it is discovered, then it is not selected.
6. Given no matching device is found within 20 seconds, when the scan times out, then `ble` stays `scanning`, `error` is `No Echelon bike found yet — pedal to wake it up`, and a new scan starts immediately.

---

## L2-002: Connection and initialisation
**Traces to:** L1-001

On selecting a device, the backend must connect, subscribe to the notify characteristic, then send the three init commands in order with write-with-response, 300 ms apart.

**Acceptance Criteria:**
1. Given a device is selected, when connection starts, then `ble` is `connecting` and `device` is the device name, or its address if it has no name.
2. Given the connection succeeds, when it is established, then `ble` is `connected` and the change is broadcast.
3. Given the connection is established, when initialisation runs, then notifications are subscribed before any init command is written.
4. Given initialisation runs, then the commands device info, resistance range and start data stream are written in that order, each with response, with at least 300 ms between writes.

---

## L2-003: Keepalive
**Traces to:** L1-001

While connected, the backend must write the keepalive command once per second and broadcast state on each keepalive.

**Acceptance Criteria:**
1. Given the bike is connected and initialised, when 5 seconds pass, then between 4 and 6 keepalive writes have been sent, each with response.
2. Given the bike is connected, when a keepalive is sent, then a state broadcast follows so time-derived fields (`displayed_seconds`) stay current.

---

## L2-004: Disconnect and error recovery
**Traces to:** L1-001

The backend must recover automatically from disconnects and from any Bluetooth exception.

**Acceptance Criteria:**
1. Given the bike is connected, when it disconnects, then `ble` becomes `disconnected`, the active bike connection is cleared, and scanning restarts.
2. Given any Bluetooth exception, when it occurs, then `ble` is `error`, `error` is `<ExceptionType>: <message>`, the state is broadcast, and scanning restarts after 3 seconds.
3. Given repeated failures, when the backend has run for 1 hour with the bike off, then the process is still running and still scanning.
4. Given the bike is off, when it is switched on and pedalled, then the backend connects within one scan cycle (≤ 20 s) without restarting.

---

## L2-005: Packet framing and counting
**Traces to:** L1-002

Every notification must be counted and logged; only well-formed packets are decoded.

**Acceptance Criteria:**
1. Given any notification, when it is received, then `packets` increases by 1, even if the packet is later ignored.
2. Given a packet shorter than 4 bytes, when it is received, then no metric changes.
3. Given a packet whose first byte is not `0xF0`, when it is received, then no metric changes.
4. Given a packet of an unknown type (e.g. `F0 D0 01 01 C2`), when it is received, then no metric changes and no error is raised.

---

## L2-006: Resistance packet decoding
**Traces to:** L1-002

A packet with type byte `0xD2` must set `resistance` to byte index 3.

**Acceptance Criteria:**
1. Given packet `F0 D2 01 0C CF`, when it is decoded, then `resistance` is 12.
2. Given a resistance packet is decoded, then `last_data_at` is set to the current time, `first_data_at` is set if it was `null`, and state is broadcast.

---

## L2-007: Workout data decoding
**Traces to:** L1-002

A packet with type byte `0xD1` and at least 13 bytes must set cadence to the big-endian 16-bit value at bytes 9–10, and derive speed from it. `speed_kmh` = round(cadence × 0.37497622, 1). `speed_mph` = round(cadence × 0.37497622 ÷ 1.609344, 1), computed from the unrounded km/h value.

**Acceptance Criteria:**
1. Given packet `F0 D1 09 00 05 00 00 00 00 00 50 00 1F` (bytes 9–10 = `00 50`), when it is decoded, then `cadence` is 80, `speed_kmh` is 30.0 and `speed_mph` is 18.6.
2. Given bytes 9–10 are `01 00`, when decoded, then `cadence` is 256.
3. Given cadence 0, when decoded, then `speed_kmh` and `speed_mph` are both 0.0.
4. Given a `0xD1` packet of 12 bytes, when received, then no metric changes.
5. Given a workout packet is decoded, then `last_data_at`/`first_data_at` are updated as in L2-006 and state is broadcast.

---

## L2-008: Set resistance command
**Traces to:** L1-003

The backend must build the set-resistance command `F0 B1 01 <level> <checksum>` and write it with response.

**Acceptance Criteria:**
1. Given level 12, when the command is built, then the bytes are `F0 B1 01 0C AE`.
2. Given level 32, when the command is built, then the bytes are `F0 B1 01 20 C2`.
3. Given the bike is connected, when a resistance of 12 is sent, then `target_resistance` becomes 12 and state is broadcast.
4. Given the bike is not connected, when a resistance send is attempted, then nothing is written and the send reports failure.

---

## L2-009: Target vs. actual resistance
**Traces to:** L1-003

The state must carry `target_resistance` (last requested) separately from `resistance` (last reported by the bike).

**Acceptance Criteria:**
1. Given `target_resistance` is 20 and the bike still reports 12, when state is read, then `target_resistance` is 20 and `resistance` is 12.
2. Given the bike then reports 20, when state is read, then both are 20.

---

## L2-010: Workout definition and validation
**Traces to:** L1-004

A workout is a non-empty ordered list of steps. Each step is `[level, seconds]` with level 1–32 and seconds > 0.

**Acceptance Criteria:**
1. Given steps `[[12,120],[24,30]]`, when submitted, then the workout is accepted.
2. Given an empty steps list, when submitted, then it is rejected with 400.
3. Given a step with level 0 or 33, when submitted, then it is rejected with 400.
4. Given a step with seconds 0 or negative, when submitted, then it is rejected with 400.
5. Given more than 100 steps, or any step longer than 3600 seconds, when submitted, then it is rejected with 400. *(New limit, not in the prototype.)*
6. Given a non-integer or missing value, when submitted, then it is rejected with 400 and no workout is started.

---

## L2-011: Workout execution
**Traces to:** L1-004

The engine must count down each step one second at a time, move to the next step when the count reaches 0, and loop back to step 0 forever, increasing `cycle` each time it wraps.

**Acceptance Criteria:**
1. Given a workout starts, then `workout` is `{steps, step:0, cycle:1, remaining:<seconds of step 0>, status}`.
2. Given the bike is connected and a step is running, when 1 second passes, then `remaining` decreases by 1 and `status` is `running`.
3. Given `remaining` reaches 0 on the last step, when the next tick runs, then `step` is 0, `cycle` increases by 1, and `remaining` is the duration of step 0.
4. Given a running step, when each tick runs, then state is broadcast.

---

## L2-012: Automatic resistance during workouts
**Traces to:** L1-004

The engine must send the step's level when a step starts (per cycle), and resend it every 5 seconds while the bike's reported resistance differs from it.

**Acceptance Criteria:**
1. Given a new step starts, when the first tick of that step runs, then the step's level is sent once.
2. Given the bike reports a resistance different from the step level, when `remaining` is a multiple of 5, then the level is sent again.
3. Given the bike reports the step level, when ticks run, then no further sends happen for that step.
4. Given a send fails, then `error` is `set resistance failed: <message>` and the workout keeps running.
5. Given the bike reconnects after a pause, when the next tick runs, then the current step's level is sent again.

---

## L2-013: Workout pause, shutdown and replacement
**Traces to:** L1-004

**Acceptance Criteria:**
1. Given a workout starts before any metric was received and the bike is not connected, then `status` is `waiting for bike` and `remaining` does not decrease.
2. Given data has been received and the bike disconnects, then `status` is `paused: bike disconnected` and `remaining` does not decrease.
3. Given data has been received, when the bike has been disconnected for more than 90 seconds, then `status` is `ended: bike shut off` and the workout stops ticking.
4. Given the bike reconnects within 90 seconds, then the workout resumes from the same `step` and `remaining`.
5. Given a workout is running, when a new workout is started, then the old one stops and the new one starts at step 0, cycle 1.
6. Given a workout is running, when it is stopped, then `status` is `stopped`, ticking stops and state is broadcast.

---

## L2-014: State model contract
**Traces to:** L1-005

The JSON state must keep the prototype's snake_case field names so the contract is stable across the rewrite.

| Field | Type | Notes |
|---|---|---|
| `ble` | string | `starting` \| `scanning` \| `connecting` \| `connected` \| `disconnected` \| `error` |
| `device` | string \| null | |
| `error` | string \| null | |
| `resistance` | int \| null | |
| `target_resistance` | int \| null | |
| `workout` | object \| null | `{steps:[[int,int]], step:int, cycle:int, remaining:int, status:string}` |
| `cadence` | int \| null | rpm |
| `speed_kmh` | number \| null | 1 decimal |
| `speed_mph` | number \| null | 1 decimal |
| `packets` | int | |
| `first_data_at` | number \| null | Unix epoch seconds |
| `last_data_at` | number \| null | Unix epoch seconds |
| `ui_clients` | int | |
| `displayed_since` | number \| null | Unix epoch seconds |
| `displayed_seconds` | number | 1 decimal |
| `ts` | number | stream messages only; Unix epoch seconds |

**Acceptance Criteria:**
1. Given the backend has just started, when `GET /api/status` is called, then the response is 200 with `ble` = `starting`, `packets` = 0, `displayed_seconds` = 0 and all nullable fields `null`.
2. Given any state, when it is serialised, then every field above is present with the stated name and type, and nulls are written as `null` rather than left out.
3. Given an exported OpenAPI document, when it is generated, then it describes every endpoint and the state schema.

## L2-015: Event stream
**Traces to:** L1-005

`GET /api/events` must return a Server-Sent Events stream (`text/event-stream`, `Cache-Control: no-cache`).

**Acceptance Criteria:**
1. Given a client connects, then it receives the current state (with `ts`) as its first `data:` message immediately.
2. Given state changes, when a broadcast happens, then every connected client receives one `data:` message with the full state JSON.
3. Given no messages for 15 seconds, when the interval passes, then the client receives a `: ping` comment line.
4. Given a client connects or disconnects, then `ui_clients` equals the number of open streams.
5. Given a client is slow and has 50 undelivered messages, when another broadcast happens, then that message is dropped for that client only and other clients are unaffected.
6. Given a client disconnects abruptly, then its resources are freed and no exception reaches the logs above Debug level.

---

## L2-016: Resistance endpoint
**Traces to:** L1-005

`POST /api/resistance` with body `{"level": <int>}`.

**Acceptance Criteria:**
1. Given the bike is connected and level 12, when called, then the response is 200 `{"sent":12}`.
2. Given level 0, 33, a non-integer or a missing body, when called, then the response is 400 with `{"error":"level must be 1-32"}` (or a ProblemDetails body carrying the same message).
3. Given the bike is not connected, when called with a valid level, then the response is 503 `{"error":"bike not connected"}`.

---

## L2-017: Workout endpoints
**Traces to:** L1-005

`POST /api/workout` with body `{"steps":[[level,seconds],...]}` and `POST /api/workout/stop`.

**Acceptance Criteria:**
1. Given valid steps, when `POST /api/workout` is called, then the response is 200 `{"started":[[12,120],[24,30]]}` and the workout starts.
2. Given invalid steps (per L2-010), when called, then the response is 400 `{"error":"steps must be [[level 1-32, seconds>0], ...]"}`.
3. Given any state, when `POST /api/workout/stop` is called, then the response is 200 `{"stopped":true}`.
4. Given no workout exists, when stop is called, then the response is still 200 and `workout` stays `null`.

---

## L2-018: Connection status display
**Traces to:** L1-006

The header must show a status pill with a coloured dot and text `<ble>` or `<ble> · <device>`.

**Acceptance Criteria:**
1. Given `ble` is `connected` and device `ECHEX-3-141844`, then the text is `connected · ECHEX-3-141844` and the dot is green.
2. Given `ble` is `error`, then the dot is red.
3. Given any other `ble` value, then the dot is amber.
4. Given the event stream fails, then the text is `server offline · retrying`, the dot is red, and the UI reconnects after 2 seconds, repeating until it succeeds.
5. Given `error` is set, then it appears in the footer; given it is `null`, the footer error area is empty.

## L2-019: Resistance card
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given `resistance` is 16, then the card shows `16` and the bar is 50% full (16/32).
2. Given `resistance` is `null`, then the card shows `--` and the bar is empty.
3. Given `target_resistance` is 20 and `resistance` is 12, then the label reads `setting 20…` and a marker sits at 62.5% of the bar.
4. Given `target_resistance` equals `resistance` (20), then the label reads `target 20 ✓`.
5. Given `target_resistance` is `null`, then no label or marker is shown.

---

## L2-020: Resistance controls
**Traces to:** L1-006

The card must have −, a numeric input (1–32, default 12), Set, and + controls.

**Acceptance Criteria:**
1. Given the input holds 18, when Set is pressed, then `POST /api/resistance {"level":18}` is sent.
2. Given the bike reports resistance 10, when + is pressed, then level 11 is sent; when − is pressed, then level 9 is sent.
3. Given no reported resistance and the input holds 15, when + is pressed, then level 16 is sent.
4. Given the input holds 40 or 0, when Set is pressed, then the value is clamped to 32 or 1, the input shows the clamped value, and the clamped value is sent.
5. Given `ble` is not `connected`, then −, Set and + are disabled.
6. Given the API returns an error, then its `error` message shows in the footer; given the request fails on the network, then the footer shows `server offline`.

---

## L2-021: Speed and cadence card
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given `speed_mph` 18.6, `speed_kmh` 30.0 and `cadence` 80, then the card shows `18.6 mph` and `30.0 km/h · 80 rpm`.
2. Given those fields are `null`, then each shows `--`.

---

## L2-022: Metric history sparklines
**Traces to:** L1-006

Each card must show a sparkline of the last 150 one-second samples.

**Acceptance Criteria:**
1. Given state has been received, when each second passes, then the current resistance and mph are added to their histories (null values are skipped).
2. Given a history holds 150 samples, when a new one is added, then the oldest is removed.
3. Given resistance history, then its y-axis maximum is the larger of 32 and the highest sample; for speed, the larger of 25 and the highest sample.
4. Given fewer than 2 samples, then the sparkline is empty.
5. Given a device pixel ratio of 2, then the sparkline is drawn at 2× resolution and stays sharp.

---

## L2-023: Footer diagnostics
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given state, then the footer shows `packets <packets> · live <round(displayed_seconds)>s · updated <local time of last_data_at>`.
2. Given `last_data_at` is `null`, then `updated` shows `never`.

---

## L2-024: Countdown clock
**Traces to:** L1-007

The hero must show the remaining step time as `m:ss`, smoothly interpolated between the once-per-second server updates.

**Acceptance Criteria:**
1. Given `remaining` is 125, then the clock shows `2:05`.
2. Given `status` is `running` and 0.5 s has passed since the last update with `remaining` 10, then the clock shows `0:10`, and the progress ring shows 9.5/`<step duration>` remaining.
3. Given no update arrives, then local interpolation advances by at most 1.25 seconds past the last value, and never goes below 0.
4. Given `status` is not `running`, then the clock does not advance locally.
5. Given no workout, then the phase label reads `No workout`, and before any state the clock shows `--:--` and the label reads `Waiting`.

---

## L2-025: Phase display
**Traces to:** L1-007

A step with level ≥ 20 is an **effort** step (orange `#ff5a36`); a level below 20 is a **recovery** step (blue `#3d9bff`).

**Acceptance Criteria:**
1. Given the current step is level 24, then the label reads `Effort · Resistance 24` and the theme colour is orange.
2. Given the current step is level 12, then the label reads `Recovery · Resistance 12` and the theme colour is blue.
3. Given the next step is `[24,30]`, then the meta line reads `Next 30 s at 24`; given it is `[12,120]`, it reads `Next 2 min at 12`.
4. Given `status` is anything other than `running`, then the status text (e.g. `paused: bike disconnected`) shows under the clock; while running it is hidden.
5. Given `cycle` is 17, then the cycle label reads `Cycle 17`.

---

## L2-026: Step timeline
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given steps `[[12,120],[24,30]]`, then the timeline shows 2 segments with widths in the ratio 120:30, blue then orange.
2. Given the current step is 1, then segment 0 is full, segment 1 fills in proportion to elapsed time and is highlighted, and later segments are empty.
3. Given each segment, then its tooltip/accessible name reads `<seconds>s at <level>`.
4. Given the number of steps changes, then the timeline is rebuilt.

## L2-027: Step-transition and countdown cues
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given the step changes (a new `cycle:step` key after the first), then a banner shows `EFFORT · <level> · GO!` or `RECOVER · <level>` for about 1.8 s, and the ring flashes.
2. Given beeps are on, when an effort step starts, then a 990 Hz tone plays for 0.35 s; when a recovery step starts, a 520 Hz tone plays.
3. Given the step is running and the whole seconds remaining drop to 5, 4, 3, 2 or 1, then the clock digits pulse; at 3, 2 and 1 with beeps on, a 660 Hz tone plays for 0.09 s.
4. Given the page loads, then beeps are off (`🔇 Beeps off`); when the toggle is pressed, they turn on (`🔔 Beeps on`) and an 880 Hz confirmation tone plays; pressing again turns them off.
5. Given the first state arrives with a workout already running, then no banner or transition beep plays.

## L2-028: Animated progress ring with renderer fallback
**Traces to:** L1-007

The hero ring must render with WebGPU, falling back to WebGL2, then Canvas 2D, and show the active renderer name.

**Acceptance Criteria:**
1. Given WebGPU is available, then the renderer label reads `WebGPU`.
2. Given WebGPU is unavailable or its shader fails to compile, then WebGL2 is used and the label reads `WebGL2`.
3. Given neither is available, then Canvas 2D is used and the label reads `Canvas 2D`.
4. Given the ring, then its arc fraction equals remaining ÷ step duration, its colour eases toward the phase colour, its glow intensifies over the final 10 seconds, and its "energy" animation speed follows cadence (capped at 100 rpm).
5. Given the device pixel ratio is above 2, then the canvas renders at no more than 2×.

## L2-029: Starting and stopping workouts from the UI
**Traces to:** L1-007

*(New. In the prototype, workouts could only be started through the API.)* The UI must let the rider build a list of steps and start or stop the workout.

**Acceptance Criteria:**
1. Given the workout panel, when the rider adds the steps `12 for 120 s` and `24 for 30 s` and presses Start, then `POST /api/workout {"steps":[[12,120],[24,30]]}` is sent.
2. Given a step with an invalid level or duration, then Start is disabled and the field shows an inline error naming the allowed range.
3. Given a workout is active, when the rider presses Stop, then `POST /api/workout/stop` is sent.
4. Given the API returns 400, then its error message is shown next to the panel.
5. Given the page is reloaded, then the last submitted steps are pre-filled from local storage.

## L2-030: Raw packet log
**Traces to:** L1-008

Every notification must be appended to `raw_packets.log` as `<epoch seconds, 3 decimals> <hex bytes, lowercase, space-separated>`.

**Acceptance Criteria:**
1. Given packet `F0 D2 01 0C CF` at 1794784639.0213, then the line `1794784639.021 f0 d2 01 0c cf` is appended.
2. Given the log reaches the configured size (default 10 MB), then it is rotated and at most the configured number of files (default 5) are kept. *(New; the prototype grew without limit.)*
3. Given logging writes are slow, then BLE notification handling is not blocked (writes are buffered off the notification path).

---

## L2-031: Persisted status snapshot
**Traces to:** L1-008

The backend must write the current state to `status.json` (indented JSON, same contract as L2-014 without `ts`).

**Acceptance Criteria:**
1. Given a broadcast, then `status.json` reflects that state within 1 second.
2. Given many broadcasts per second, then writes are throttled to at most 2 per second, and the final state is always written. *(New; the prototype wrote on every broadcast.)*
3. Given the file is read while being written, then it is never partial (write to a temp file, then rename atomically).

---

## L2-032: Displayed-time tracking
**Traces to:** L1-008

`displayed_seconds` measures how long live data has been continuously on screen.

**Acceptance Criteria:**
1. Given at least 1 UI client is connected and `last_data_at` is within the last 5 seconds, when a broadcast happens, then `displayed_since` is set (if `null`) and `displayed_seconds` = round(now − `displayed_since`, 1).
2. Given there are no UI clients or data is more than 5 seconds old, when a broadcast happens, then `displayed_since` is `null` (and `displayed_seconds` keeps its last value).

---

## L2-033: Structured logging and health
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given BLE state transitions, API errors and workout status changes, then each is logged through `ILogger` with structured fields (state, device, error).
2. Given `GET /health`, then the response is 200 when the HTTP host is up, and the body reports the current `ble` state.
3. Given per-packet events, then they are logged at Trace level only, so default logs are not flooded.

---

## L2-034: Network exposure
**Traces to:** L1-009

**Acceptance Criteria:**
1. Given default configuration, then the backend listens only on `127.0.0.1:8787`.
2. Given the backend is configured to listen on a non-loopback address, then it refuses to start unless an API key is configured.
3. Given CORS, then only explicitly configured origins are allowed (in development, the Angular dev server origin only); by default no cross-origin requests are allowed.

---

## L2-035: API authentication
**Traces to:** L1-009

When an API key is configured, every `/api/*` endpoint must require it.

**Acceptance Criteria:**
1. Given an API key is configured, when a request is made without the `X-Api-Key` header or with a wrong one, then the response is 401 and no command reaches the bike.
2. Given the correct key, then the request is processed normally.
3. Given the event stream (which can't send custom headers from `EventSource`), then it accepts a short-lived token from `POST /api/events/token` in a query parameter, valid for 60 seconds and usable once.
4. Given keys are compared, then the comparison is constant-time.
5. Given loopback-only mode with no key configured, then requests are allowed without a key.

---

## L2-036: Input validation and hardening
**Traces to:** L1-009

**Acceptance Criteria:**
1. Given a request body over 16 KB, then the response is 413.
2. Given malformed JSON or a wrong content type on a POST, then the response is 400 (or 415) and no stack trace or internal detail is returned.
3. Given more than 20 control requests (`/api/resistance`, `/api/workout*`) per second from one client, then the extra requests get 429.
4. Given any response, then it includes `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and a Content-Security-Policy that allows only same-origin scripts, styles and connections.
5. Given unhandled exceptions, then the client receives a generic 500 ProblemDetails and the detail goes only to the server log.
6. Given device names and error strings from Bluetooth, then the UI renders them as text, never as HTML.

---

## L2-037: Live-data latency
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given a BLE notification is received, then the matching state message reaches a connected browser on the same machine within 100 ms (p95).
2. Given 10 concurrent event-stream clients, then the p95 delivery latency stays under 150 ms.
3. Given `GET /api/status`, then the p95 response time is under 20 ms.

---

## L2-038: Resource use over long rides
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given a 4-hour ride with 1 client connected, then backend memory grows by no more than 20 MB from its warm-up level.
2. Given idle state, then backend CPU use averages under 2% of one core.
3. Given the dashboard is open for 4 hours, then browser memory for the tab grows by no more than 50 MB, and the animation loop holds ≥ 55 fps on a mid-range laptop.
4. Given the browser tab is hidden, then animation frames stop (or are reduced) and resume when it is visible again.

---

## L2-039: Graceful lifecycle
**Traces to:** L1-010

**Acceptance Criteria:**
1. Given the process receives a stop signal, then it stops the workout loop, disconnects from the bike, closes event streams and exits within 5 seconds.
2. Given the Bluetooth adapter is missing or off at startup, then the HTTP API still starts, `ble` is `error` with a clear message, and the backend retries until the adapter is available.

---

## L2-040: Responsive layout
**Traces to:** L1-011

**Acceptance Criteria:**
1. Given viewport width < 576 px (XS), then the metric cards stack in a single column, the hero ring is at most 92% of the viewport width, the header stays on one line or wraps without overlapping, and nothing scrolls horizontally.
2. Given 576–767 px (SM), then the cards stay single-column and the clock digits scale between 64 px and 124 px with the viewport.
3. Given 768–991 px (MD), then the cards show two columns.

## L2-041: Accessibility
**Traces to:** L1-011

The UI must meet WCAG 2.2 AA.

**Acceptance Criteria:**
1. Given a keyboard-only user, then every control (beeps toggle, −, level input, Set, +, workout panel) is reachable with Tab in a logical order and shows a visible focus indicator.
2. Given a screen reader, then −/+ have the names `Decrease resistance` / `Increase resistance`, the level input is named `Resistance level`, and the decorative canvas is hidden from assistive tech.
3. Given a step transition, then a polite live region announces the new phase (e.g. `Effort, resistance 24, 30 seconds`); the per-second clock is not announced.
4. Given `prefers-reduced-motion: reduce`, then the digit pulse, banner animation and ring time animation are disabled, and colours change instantly.
5. Given text and controls, then their contrast is at least 4.5:1 (3:1 for large text and UI components) on the dark background.
6. Given an automated axe-core scan of the dashboard, then it reports no serious or critical violations.

## L2-042: Backend technology and structure
**Traces to:** L1-012

**Acceptance Criteria:**
1. Given the backend solution, then it targets the current .NET LTS and uses ASP.NET Core minimal APIs.
2. Given the BLE layer, then it is behind an `IBikeTransport` interface (scan, connect, subscribe, write, disconnect events), with a simulated implementation used by acceptance tests.
3. Given the BLE loop, workout engine and state broadcaster, then each runs as a hosted service, and shared state is updated thread-safely (single-writer or locked).
4. Given packet decoding, checksum and command building, then they live in a pure library with no Bluetooth or HTTP dependencies and have unit tests for every example in L2-005–L2-008.
5. Given configuration (port, bind address, API key, log paths, CORS origins), then it comes from `appsettings.json`, environment variables or command-line options.
